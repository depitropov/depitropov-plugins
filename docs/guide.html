A framework for AI coding runs

Orchestra

Many tools can run AI agents that write a spec, a plan and code. Orchestra adds the two things that make the result trustworthy and reusable: swappable parts and quality gates that cannot be skipped.

What it does

Enough to decide if you want it.

What orchestra delivers

Agents that write specs and code are common. Orchestra is about how those agents are put together and checked.

1 · Swap any part, keep the rest

The steps of a run, the knowledge of your language stack, and your project's rules are three separate plugins. They connect through fixed contracts in the orchestra core. Change one and the others do not notice.

2 · Gates that always run

After the code is written, orchestra runs a fixed series of checks called gates. The workflow brings its gates, the stack brings its own, and orchestra runs all of them in one fixed order, with the full build first and last. A gate fixes what it finds and commits the fix. The AI cannot skip a gate, reorder the gates, or call the work done while the build is red.

And on top of that

Order in code

Plain code decides each next step from files on disk. The AI only does the step it is given, so a run cannot drift.

Stops only when it must

Missing business facts and real product decisions come to you, before work is built on a guess. Everything else is decided and recorded.

Every run explained

A committed report: what ran, what was assumed, what was fixed, and what a human should check. Same files on Claude Code and Codex.

The result of one run

One run takes one task. It ends with one of three results. Here is what each looks like.

A branch, done

Commits on a new branch. The full build is green. Nothing is pushed.
Example
task/add-a-vip-discount-to-the-order feat: add a VIP flag to the customer feat: apply the VIP discount to the total fix(logic-review): test rounding at 0.005 orchestra: run notes (done)

A report

What ran, what the agents assumed, and what a human should look at.
Example
Status: done Results spec ............ ok plan-check ...... ok patch 2 code-1 .......... ok logic-review .... ok patch 1, evaluate 1 Assumptions rounded HALF_UP to 2 decimals Evaluate OrderService.java:42 a null customer now throws

Or a question

The run stops before it builds on a guess. You answer, run again, and it goes on.
Example
business fact: the VIP discount rate — options: 5% | 10%

Answer in decisions.md:
## business-facts
- the VIP discount rate → 10%

Why use it

One AI agent in one long chat can write code. But it forgets rules as the chat grows, it reviews its own work kindly, and it fills gaps with guesses. Orchestra changes the shape of the work:

Without orchestraWith orchestra
Rules get lost in a long context.Each step is a fresh agent with a small prompt and one job.
The author reviews its own code.Every reviewer is a new agent. It sees the requirements, not the author's story.
The model skips or reorders steps.Code fixes the order. The model only runs the step it is given.
A missing price or rate is guessed.A missing business fact stops the run and asks you.
Tests pass but prove nothing.A reviewer checks that each test fails on a likely wrong version of the code.
Each team builds its own pipeline.Swap the stack plugin (Java today) or the workflow. The rest stays.
It works on one AI tool.The same files run on Claude Code and Codex.

One steady workflow, many gates

Orchestra splits a run into two parts that change at different speeds. The workflow is the same for every project: the same steps, in the same order, with the same places to stop. The gates differ per project: each level adds the checks it knows about. So you always know what a run will do, while the checks fit the code in front of it.

Each level adds its own gates

LevelKnows aboutAdds
OrchestraAny projectThe full build, first and last. The fix loop, the round limits, triage and the report for every gate.
WorkflowAny languageChecks that need no stack: was the plan done, is the logic right, can each test fail.
StackOne language and its toolsThe build command, tool gates (coverage, mutation, formatting) and reviewers for its conventions.
ProjectYour code baseWhich gates are on, how many fix rounds, your own patterns. Later: its own gates and a build that overrides the stack.

A gate is declared as data by the level that owns its knowledge. The level never decides when or how the gate runs. Orchestra does that, the same way for every gate. That is why a new stack cannot break the workflow, and a new workflow does not need to know Java.

Write small, check big

The coder gets a small context: its part of the plan, the code it touches, and a short guide of 5 to 15 rules. The full rules of each topic live in a gate after the code, one topic per gate. Long rule lists are followed worse as the context grows. A focused reviewer with one topic and the finished code follows them better.

The rules every gate follows

One gate, one concern

Each gate checks one thing, and the plugin that knows that thing declares it.

Machines first

The build and tool gates run before reviewers, so reviewers judge code that already compiles and passes.

Only what changed

A gate runs only when the change touches its files or patterns. The report lists what was skipped and why.

Fix in place, once

A reviewer fixes its findings and commits, and never re-reviews its own fix. A tool gets a fixed number of fix rounds.

Leftovers go to you

What a gate cannot or should not fix goes to the report as Evaluate. The run goes on. No endless loops.

Green is the proof

The last gate is always the full build. Gates in finish must not change behaviour, because nothing reviews after them.

Prepare

plain code, no AIstops on a dirty tree

Orchestra starts from a fresh copy of your default branch and creates a new branch for the task. Your own work is safe: if you have changes that are not committed, the run stops and names the files.

  1. tree clean?
  2. →
  3. check out the default branch
  4. →
  5. git pull --rebase
  6. →
  7. create task/<name>
  8. →
  9. record the base commit
  10. →
  11. save the task text

The default branch comes from origin/HEAD. A taken branch name gets -2, -3. The base commit is what every later review compares against.

prepare() in orc-standard-workflow/bin/next.js. It writes tmp/runs/<branch>/run.json (base, branch, brief path, notes folder) and docs/runs/<branch>/task.md.

Spec

AI agent, freshwrites brief.md

An agent turns your task into a short brief: the goal, the acceptance criteria as given-when-then, what is in and out of scope, the other services and repos it touches (its integration points), and its assumptions. Every later step is checked against this brief, so it is the contract of the run.

  1. read the task
  2. →
  3. read AGENTS.md and the code
  4. →
  5. external fact? read it at its source
  6. →
  7. open question?
  8. →
  9. technical: take a default, record it
  10. ·
  11. business fact: mark it
  12. →
  13. write brief.md

A technical choice (rounding, null handling, order of two steps) gets a boring default. A business fact (a rate, a price, a limit, who qualifies) never gets a value. A fact from outside the project is read at its source (a sibling checkout, an API contract, a schema or a migration) or recorded as an assumption. A repo the task names is read only: its needed changes become follow-ups. See who does what.

Skill orc-standard-workflow:spec. Dispatched by stage(ctx, 'spec', …) in next.js. Result in spec.result.json, with an assumptions list.

Missing facts

plain codeasks you

If the brief needs a fact that only you know, the run stops here and asks. This is before any plan or code, so nothing is built on a guessed value. When the brief has no open fact, this step does nothing.

  1. find "business fact:" lines
  2. →
  3. stop with the questions
  4. →
  5. you add ## business-facts
  6. →
  7. run again
  8. →
  9. plan writes the values into the brief

See answer a question for the exact format.

openFacts() in next.js reads the brief with a regex. It writes business-facts.result.json so the stop shows in the report.

Plan

AI agent, freshuses the stack's plan guide, if anywrites plan.md

An agent splits the brief into small, ordered tasks. Each task names its files and the tests that prove each acceptance criterion. The plan has no code.

  1. load the plan guide, if any
  2. →
  3. apply your answers to the brief
  4. →
  5. read the affected files
  6. →
  7. write tasks T1, T2, …

A task has at most about four files and one job. Notes may hold a signature or ten lines of pseudo-code, no more.

Skill orc-standard-workflow:plan, with input guide when the stack has a plan guide and the project does not disable it. orc-java-stack has a code guide only, with the test-command facts. It has no plan guide (S68).

Plan check

AI agent, freshcan ask youfixes the brief and plan

A second agent, which did not write the plan, checks the brief and the plan against the real code and fixes them. A wrong plan is cheapest to fix here, before any code exists. It also checks that every external fact has a source, and it stops the run when the task needs a change in a repo the task does not name.

  1. every criterion has a test?
  2. →
  3. files and signatures exist?
  4. →
  5. in scope, small, no over-building?
  6. →
  7. external facts sourced?
  8. →
  9. triage
  10. →
  11. a real decision? stop
  12. ·
  13. else patch

After it, code counts the task headings ### T1…Tn. A plan with gaps in the numbers sends the run back to plan check.

Skill orc-standard-workflow:plan-check, which invokes orchestra:triage. planTasks() in next.js counts the tasks.

Code

AI agents, one per 2 tasksuses the stack's code guide, if anyone commit per task

Coder agents implement the plan, two tasks each by default, with tests. Each task becomes one commit. A coder never deletes or disables a test to get a pass.

  1. load the code guide, if any
  2. →
  3. do the task
  4. →
  5. write its named tests
  6. →
  7. run the affected tests
  8. →
  9. commit
  10. →
  11. log it, record assumptions

The coder runs only the tests it touched. Orchestra runs the full build after it. A task done another way than the plan says is written down as a deviation. Detail inside a task, such as an extra check, is the coder's call: it goes into code.md. When a coder fails and the run goes on, the next coder finds the reason in the implementation log.

Skill orc-standard-workflow:code, dispatched as code-1, code-3, … The chunk size is the config key tasks-per-coder.

Implementation check

full build, then reviewersa red build fails the run

Is the code correct and sound? The full build and tests run. Then one reviewer checks that the plan was done, and a second checks the logic against the brief. They fix what they find and commit the fixes.

  1. build (up to 3 fix rounds)
  2. →
  3. tool checks
  4. →
  5. plan-conformance
  6. →
  7. logic-review

See gates and phases and the two reviewers.

runner.step() in orchestra/lib/runner.js, with the gate list from both plugins' orchestra.json.

Conventions check

stack reviewersno gates yet

Does the code follow your team's conventions? Stack reviewers check things like test style, and fix them. Only the reviewers that concern the changed files run. The Java reviewer here is testing. The ops reviewer runs earlier, in implementation-check.

  1. select by changed files
  2. →
  3. tool checks
  4. →
  5. review agents

collect(), select() and plan() in orchestra/lib/gates.js.

Finish

cosmetic passes, then builda red build fails the run

Cosmetic passes (comments, logging, formatting) clean up. Then the full build runs one last time. A green build is the proof that the branch is good. Nothing runs after it.

  1. review agents
  2. →
  3. formatter
  4. →
  5. final build

A finish check must never change behaviour, because no review comes after it.

PHASE_ORDER.finish in gates.js. The build is skipped when HEAD is the last green commit and the tree is clean.

Use it

Enough to run it.

Set up and start

Your project needs four things:

  • The three plugins installed: orchestra, orc-standard-workflow and a stack plugin such as orc-java-stack.
  • A committed .orchestra/config.json that names the plugins (below).
  • A .gitignore with .orchestra/*, !.orchestra/config.json and tmp/.
  • An origin/HEAD that points to the default branch, and project instructions in AGENTS.md, not CLAUDE.md. In Claude Code, one CLAUDE.md turns off every AGENTS.md.
// .orchestra/config.json
{
  "workflow":     { "plugin": "orc-standard-workflow" },
  "stack-skills": { "plugin": "orc-java-stack" }
}

Then ask your AI tool:

orchestra run "Add a VIP discount to the order total"   # start from text
orchestra run docs/tasks/vip.md                          # start from a file
orchestra run                                            # continue a stopped run

Before it starts, orchestra tells you that it will check out the default branch, pull it, and create the task branch. A run can take a while, because the full build runs more than once.

Answer a question

A run stops for you only when a real decision is needed. The report lists each question with its options. You answer in a file, then run again.

Add a new section at the end of docs/runs/<branch>/decisions.md, named after the step that asked. Write one line per question:

## business-facts
- the VIP discount rate → 10%
- who counts as VIP → customers with 10 or more orders this year

For business facts, every question needs its own line. When a line is missing, the run stops again with the same questions. Then run orchestra run with no task, on the task branch. You can also give the answers in the chat: orchestra writes the section for you, in your words.

Two rules

Text added to an old section is not read as an answer. Always add a new section. And do not change other files while a run is stopped: on resume, orchestra stops if it finds changed files, so your work is never mixed into the task.

When a run fails

A failed run shows the reason and the report. Fix the cause if it is yours (for example a dirty tree), then run orchestra run again. The failed step runs again. Steps that finished never run again.

Read the report

The report is in docs/runs/<branch>/report.md, next to the brief, the plan and the review notes. Read these parts first:

PartWhat to do with it
AssumptionsTechnical choices the agents made on their own. Check that you agree.
DeviationsTasks the coder did another way than the plan says, with the reason. Check that the change of direction is right.
Integration pointsThe other services and repos the task touches. A change that another repo needs is a follow-up for you: the run never changes another repo.
EvaluateFindings a reviewer chose not to fix, because the fix costs more than the problem, or because only a human can judge it. Each has a file:line.
ResultsEvery step in order, with its counts: how many findings were patched, sent to you, or dropped.
Skipped checksChecks that did not run, and why (for example "no changed file matches").
DecisionsA copy of your answers, so the report is the full record.
CommitsThe commits of the run and a list of the changed files, without the run notes.

The notes folder is committed. It goes to the default branch with your pull request, so the reasons stay next to the code.

Change what runs

Orchestra is built from parts you can swap. The workflow says which steps run and in what order. The stack brings the build command and the rules for one language. Your project config picks both and tunes them.

Orchestratororchestra
The engine: the entry, the loop, the checks, the report. You do not change it.
Workfloworc-standard-workflow
The steps of a run and their order, plus its own two reviewers. Works with any stack.
Stack Skillsorc-java-stack
Java with Maven: the build, a code guide, fix guides, and six gates: ops, testing, comments, logging, layout and Spotless.
Project.orchestra/config.json

Rules for one project that override the stack, including its build.

What you can set

{
  "workflow": {
    "plugin": "orc-standard-workflow",
    "tasks-per-coder": 3                      // tasks per coder agent (default 2)
  },
  "stack-skills": {
    "plugin": "orc-java-stack",
    "disable": ["code-guide"],                // turn off a check or a guide by name

A stack can also offer its own keys, for example a pattern that marks your entity classes. You set them in the same section. Today orchestra run checks the plugin names and slots. A full check of every key (orchestra check) and a setup wizard (orchestra init) are planned.

How it works

The flow, without code.

Who does what

Three kinds of actor take part in a run. Plain code makes every decision about order. AI agents do the work, each one fresh. You answer only real questions.

Technical choice or business fact

This split runs through every step. A technical choice has a sensible default: the rounding mode, null handling, the order of two steps. The agent takes the default and records it, and the report shows it to you. A business fact never has a default: a rate, a price, a limit value, who qualifies. An invented fact is the one mistake a later review cannot see, because the code and the tests agree with each other and both are wrong. So business facts always come to you.

Gates and phases

After the code is written, a series of checks runs. Each check is called a gate. A gate is a command (a tool, which passes or fails by its exit code) or a reviewer (an agent, which reads the change and fixes what it finds). Gates are grouped into three phases, always in this order:

A gate hasValuesMeaning
phaseimplementation-check, conventions-check, finishWhere it runs.
kindtool or agentA command, or a reviewer.
fixself, fixer, noneA formatter fixes itself; the fixer agent fixes a tool's findings; or report only. A reviewer always fixes its own findings, once.
selectionfiles, grep, when, alwaysWhen it runs: a file pattern, a text pattern in the changed files, a rule in words, or always.
max_roundsa number, default 2How many fix rounds a tool gets.

The build and the fix loop

The build is special. It is not a gate you can turn off. It runs first in implementation-check and last in finish, and it produces the test coverage that other tools read. When a tool or the build fails, a fixer agent gets the raw output and a fix guide from the stack, fixes only what the output reports, and commits. Then the tool runs again.

The two reviewers

The workflow brings two reviewers. They split one job on purpose, and each one sees different documents:

plan-conformance checks that every task of the plan is done, every named test exists, a task done another way is declared as a deviation, and nothing falls outside the brief's scope. The plan sets the direction, not every line: an extra check or a helper inside a task is not a deviation (S67). It gives no verdict on correctness.

logic-review first writes down what each acceptance criterion requires and one likely wrong version of the code (the wrong rounding mode, < for <=, a missing null check). Only then does it read the code. Each test must fail on that wrong version. A test that would pass on wrong code is a finding. Then it hunts for bugs. Last, it reads code.md: a recorded choice that changes behaviour, such as a check that throws, needs its own test too.

Why the split: the plan is the author's view of the code. A reviewer who reads it tends to check "did the code follow the plan" and to take over the plan's blind spots. Research shows that author framing makes AI reviewers miss bugs (R5).

Triage: what happens to a finding

Every reviewer puts each finding into exactly one bucket. The bucket decides the action.

DecideStop and ask you, before any fix.
PatchFix it now, with the smallest fix.
EvaluateDo not fix. Show it in the report.
NoiseDrop it, with one line why.

Each finding is rated on five axes: where it comes from, the risk, the risk of the fix, how likely it is, and what kind of problem it is. Decide needs two things together: a real choice between options with different trade-offs, and a reason the agent cannot make the call. Either the answer is a product question nobody wrote down, or the choice reshapes the work and no option is clearly better. When the agent can reason to an answer, it must make the call and write why. Asking you about something it could decide is a failure too.

Gates check the code. Other guardrails keep the run itself safe. Most are code, not instructions, because code cannot be talked out of a rule.

Files

A run keeps two folders, both named after the branch. What code needs to choose the next step stays in a git-ignored folder. What you read is committed.

Why it works this way

For when you want to argue with a choice.

How decisions are made

Every choice in orchestra has a numbered record. The bigger ones have research or a real run behind them. You can trace any rule back to its reason.

FileRole
docs/TENSIONS.mdThe index. One row per decision, S1 to S68 today, with its source. Also the open points for later.
docs/DECISIONS.mdThe full record of a decision that weighed options: question, options, evidence, choice, cost and risk.
docs/research/Research written before the decision. Each finding has a source and a strength: strong, medium or weak.

Records are never rewritten. A newer decision replaces an older one and names it.

The research

NoteQuestionAnswerLed to
R1How do AI tools load project instructions?Claude Code reads AGENTS.md only when there is no CLAUDE.md, and a repo cannot change that.Projects use AGENTS.md.
R2How to keep a fixed step order on every AI tool?Tool-specific workflow scripts do not travel. A small program that reads files and prints the next step does.The order lives in plain Node code.
R3Give the coder all the rules, or check them after?Both, unevenly: 5 to 15 short rules while writing, the full rules in focused reviewers after. Medium confidence.Short guides, then gates.
R4Can an agent start its own agents?Claude Code yes. Codex not by default.All agents start from the main session.
R5Should the logic reviewer see the plan?No. Author framing makes reviewers miss bugs (measured).Two separate reviewers.

Example of the evidence

When a pull request text said the code was "bug-free", AI reviewers found far fewer of its security bugs: one model dropped from 97% to 4%, another from 68% to 9%. Removing the text recovered most of them. This is why logic-review never reads the plan.

Each real run on a sample project fed back into the design. The first runs led to clearer errors, a skip for repeated builds, the Evaluate list in the report, the assumptions list, the business-fact stop, and the rebuilt logic review.

Under the hood

The code explains the rest.

Plain Node, standard library only, about 830 lines. This level gives you the map. Read the code for the detail.

One call, end to end

No process keeps state in memory between two agents. Every call starts from the files on disk, so a stop, a crash or a closed terminal costs nothing.

Step lifecycle

Each workflow step and each reviewer gate follows the same small state machine, driven by its result file.

Plugin contracts

For people who write a workflow or a stack plugin. A plugin finds its own folder through its manifest skill, so orchestra never guesses an install path:

Each plugin ships a declaration, orchestra.json. It is data only. Orchestra decides when and how to use it.

{
  "slot": "stack-skills",
  "build":  { "run": "./mvnw -B -fae $(grep -q spotless-maven-plugin pom.xml 2>/dev/null && echo -Dspotless.check.skip=true) verify",
              "guide": "fix-build", "max_rounds": 3 },
  "guides": { "code": "code-guide" },

Glossary

Orchestrator
The orchestra plugin and its single entry, orchestra run.
Workflow
The plugin that sets the steps of a run and their order.
Stack Skills
The plugin with the build, guides and reviewers for one language stack.
Slot
A named place in the config that one plugin fills: workflow or stack-skills.
Declaration
A plugin's orchestra.json. Data only.
Brief
The goal and acceptance criteria of a run. Every check compares against it.
Phase
implementation-check, conventions-check, finish: the three groups of gates.
Gate
One check after the code: a tool (a command) or an agent (a reviewer).
Build
The full build and tests. It runs first and last. Not a gate.
Fixer
The agent that fixes a failed tool, using the tool's fix guide.
Guide
Short rules for the planner or the coder, from the stack.
Triage
Sorting a finding into Decide, Patch, Evaluate or Noise.
Business fact
A product value no agent may invent: a rate, a price, a limit, who qualifies.
Technical choice
A choice with a sensible default, taken and recorded.
Notes folder
docs/runs/<branch>/. What you read. Committed.
Run folder
tmp/runs/<branch>/. What code reads. Git-ignored.
S<n>, R<n>
A recorded decision, a research note.
